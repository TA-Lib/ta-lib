# WASM engine for the npm package

**Status:** batch built. The default entry of the `ta-lib` npm package can run the batch tier of every function that cannot reach a transcendental call in a WebAssembly engine, behind the API of [typescript-api-design.md](typescript-api-design.md), but the routing table (W12) is empty, so only the test modes (W15) send a call there. Not built: streams in WASM (W16's second step), a bundler test of the `default` entry's `ready()`, and the open rows. The TypeScript library of [typescript-backend.md](typescript-backend.md) stays, as the `ta-lib/js` entry and as the default entry's fallback. Rows marked Ruled are the owner's; Adopted rows stand unless he reopens them; an Open row names the measurement that settles it.

## 1. Scope

- **What ships.** One package, two entries. `ta-lib` runs a batch call in WASM when the routing table names it (W12), the call meets W13 and the runtime passed the load checks (W4), and in the `./js` function otherwise; its lookbacks, streams and metadata are the `./js` ones. `ta-lib/js` is the TypeScript library alone and never loads WASM.
- **Same values.** The two engines are bit-identical on every call the default entry sends to WASM, so which one answers changes speed only, and the default entry chooses by itself. On a non-finite input the sign and payload of a NaN result may differ between the engines. A call that can reach a transcendental function stays in TypeScript (W10).
- **What does not ship:** a WASM-only entry, an API that must be awaited before its first call, one WASM module per function.

## 2. Decisions

| # | Decision | Choice | Why | Status |
|---|---|---|---|---|
| W1 | Engine | A WASM engine generated beside the TypeScript library, in the same npm package | Software `fma` is TypeScript's dominant cost ([D9](typescript-backend.md)); a hardware fused multiply-add in WASM removes it | Ruled (owner, 2026-11-11) |
| W2 | Entries | `"."`: a generated layer per function that calls WASM when it is loaded and the `./js` function otherwise. `"./js"`: the TypeScript library as it is, with no routing and no WASM glue. The default entry exports every name `./js` exports, plus `ready` and its status types; the two share `Core`, `TALibError`, the enums and the result types | Whoever must not load WASM (a strict Content-Security-Policy, a size budget) imports `ta-lib/js` and gets today's code. Everyone else gets the fast path with no code change | Ruled (owner, 2026-11-11) |
| W3 | FMA | `f64x2.relaxed_madd` (relaxed SIMD), used only where W4 proves it fused | Fused, it gives C's bits. Relaxed SIMD lets an engine compute it unfused, so it is trusted only after the check | Ruled (owner, 2026-11-11): hardware FMA comes first |
| W4 | Load checks | The module compiles, and one multiply-add whose fused and unfused results differ returns the fused one, on operands that reach the module at run time. A failure of either leaves the TypeScript path in place and throws nothing. `ready()` resolves to `{ engine, reason }`: `'wasm'` or `'js'`, and for `'js'` the step that failed (bytes not importable, compile, instantiate, the fused check), that the engine is not loaded yet, or that traps turned it off (W17). `getRuntimeInfo` from `ta-lib/metadata` reports the same state of the same engine as the keys `wasm.engine` and `wasm.reason`, which only TypeScript answers; asking loads nothing | Compilation fails where relaxed SIMD is missing and where a Content-Security-Policy forbids WASM; there is no way to ask without trying. Constant operands could be folded at build time, and the probe would then pass on a CPU that does not fuse | Adopted; reported by `getRuntimeInfo`: Ruled (owner, 2026-11-12), every backend answers the common keys and only the backend that has a thing answers a key describing it |
| W5 | API | Unchanged and synchronous: no top-level await ([D3](typescript-backend.md)), no call that must be awaited first | The fallback is what makes this possible in a browser, which compiles a module of this size only asynchronously | Adopted |
| W6 | Settings | `Core` stays the JavaScript object of [D12](typescript-backend.md) and the only owner of unstable periods and candle settings. The module holds only the default settings, and until a `Core` can be passed to it, a call whose `core` is not `Core.DEFAULT` runs in TypeScript | One source of truth whichever engine answers. A subclassed or non-default `Core` read through the module's own copy would silently answer with other settings | Adopted |
| W7 | Loading | Node, Deno and Bun instantiate synchronously on the first call the routing table sends to WASM, not at import. A browser loads the engine only when the caller awaits `ready()`; before that, and without it, every call runs TypeScript. `ready()` takes no argument; settings stay on `Core` (W6) | A script that never reaches a routed call pays nothing, and importing the package compiles nothing. In a browser an explicit call fetches the bytes only for a caller who asked, and a page whose Content-Security-Policy forbids WASM logs no violation unless it called | Ruled (owner, 2026-11-11): explicit `ready()` in browsers. First-call instantiation: Adopted |
| W8 | Source | The module is the generated Rust crate built for `wasm32-unknown-unknown`, behind the generated export crate `ta_codegen/output/wasm`, one `extern "C"` batch export per function. The `ta-lib` crate's fused sites are the `fmadd!` macro, whose wasm32 arm is `f64x2.relaxed_madd`, and that crate stays `#![forbid(unsafe_code)]`; the slices over linear memory are formed in the export crate, which declines a misaligned slice and an output overlapping any other slice. `scripts/build.py wasm` builds it with relaxed SIMD on and both auto-vectorisers off | The crate builds for that target with its own allocator; a bad index traps where C would corrupt linear memory. The generated C built for wasm32 gives the same bits and, candlesticks apart (#594, #580), the same speed, and would need a C library for the target. With relaxed SIMD on, LLVM turns every vectorised float select into a relaxed min or max, and no spelling of the source avoids it; W-O5 is the way back to vectorised loops | Adopted |
| W9 | Modules | One, exporting the batch tier of every function W10 admits, whatever the routing table holds; streams join it at W16's second step | A function taking an MA type at run time carries every moving average, so a split by family would repeat that code in each part. A routing-table edit changes no binary, and the test modes reach every export | Adopted |
| W10 | Transcendental calls | A call that can reach a transcendental function ([D11](typescript-backend.md)'s predicate: the function carries `uses_transcendental`, or an MA-type parameter selects MAMA or ALMA) runs in TypeScript: such a function has no export, and an export declines an MA type that selects one. The module imports nothing | A libm inside the module differs from the JS engine's `Math.*` in the last bit, silently, and a recursive filter amplifies it; an import needs `unsafe` in the `ta-lib` crate. Either way these calls gain nothing in batch | Adopted |
| W11 | Stream class | Once streams move to WASM (W16), one `<N>Stream` per indicator in the default entry, holding a WASM handle or the `./js` stream, each method choosing by that. Until then the default entry re-exports the `./js` stream class and openers | A call site sees one class whichever engine answers | Adopted |
| W12 | Routing | A table, `ta_codegen/input/wasm_routing.yaml`, says, per function and tier, from how many bars the WASM path is taken when the engine is loaded; absent means never. An entry is set only from timings of the public call on intel-1, amd-1 and macos-1, by medians, where WASM is faster on each by a margin | The copy into and out of linear memory outweighs the gain on cheap functions with no fused site and on short series, and the functions that lose differ between x86 and ARM64 | Adopted |
| W13 | Argument contract | `./js` is the authority. The default entry takes the WASM path only when the routing table names the tier at the input's length, or a test mode forces it (W15), and: the options are omitted or an object `./js` accepts as one; no output buffer is passed; `core` is omitted or `Core.DEFAULT`; each range bound and integer parameter is an int32 and each real one a number; every input has the same length, which for a typed array must equal its built-in length; the range lies inside the input; and the call's bytes fit the memory budget (W17). It converts every input with the `./js` entry conversion before it touches linear memory, sizes each slice in linear memory to that length, and derives its views after the last step that can run caller code. The export declines an enum value it does not know or that W10 keeps in TypeScript; the Rust public tier validates the rest. Any other call, any call WASM declines or rejects and any trap is handed to the `./js` function with the caller's original arguments, which answers or throws; an argument whose getter or `valueOf` has a side effect therefore runs twice on a fall-through | A rejection always carries the `./js` message and code. Rust sees only the slices the glue builds, never the caller's arrays, so every check on a caller's buffer stays on the `./js` side. A caller's `valueOf` or getter can run during a copy and grow linear memory, which detaches a view taken earlier and drops the rest of the copy silently | Adopted |
| W14 | Packaging | The module ships inside the package as one JavaScript file holding its bytes (base64), `runtime/wasmBytes.js`, never committed: `scripts/ts_wasm_bytes.mjs` writes it from `bin/ta_lib.wasm` after `tsc`, into `dist/` for `build-libraries` and beside the server's compiled library for the server build, and refuses a `bin/ta_lib.wasm` older than the crates' sources. `exports["."]` has a `node`, `bun` and `deno` condition whose entry imports that file statically, and a `default` entry whose `ready()` imports it dynamically; `"."` and each condition list `types` first, and `sideEffects` names only the static entry. `"./js"` imports neither. `./metadata` calls the `./js` functions | No `.wasm` asset for a bundler to lose, no `node:` import in the library ([D3](typescript-backend.md)), and a browser bundle that never calls `ready()` does not carry the bytes. A runtime that forbids compiling from bytes (some edge runtimes) stays on TypeScript. Without the `sideEffects` entry a bundler may drop the static entry's hand-over of the bytes | Adopted |
| W15 | Gates | Two test modes ignore the routing table and route every call W13 admits: `force` falls through as the table does, `strict` throws where a call `./js` accepts would fall through. The generated server started with `--engine=wasm` runs its batch correctness calls through the default entry in `force` mode and adds per-call engine evidence to each reply; ta_regtest runs it as `tswasm` in `--codegen` and `--xlang-hash`, and its transport fails the run on a fall-through the server does not class as by design and on an exported function that never ran in WASM ([section on `tswasm`](../src/tools/ta_regtest/CLAUDE.md)). The generated `test/engineParity.test.ts` runs in `strict` mode and compares raw bits with `./js` for every exported function, over default, minimum and drawn parameter sets, every MA type W10 admits included. `scripts/check_wasm_module.py` decodes the module and fails on an import or on any relaxed-SIMD instruction other than `f64x2.relaxed_madd` | A fall-through answers correctly from TypeScript, so a gate that neither throws on one nor counts them makes every engine comparison TypeScript against TypeScript and passes. The server uses `force` because the harness also sends calls `./js` accepts that fall through by design (a non-default `core`, inputs of unequal length, an MA type W10 keeps in TypeScript), which `strict` would turn into errors; the evidence tells those from a defect. With relaxed SIMD enabled for a whole crate the compiler also picks relaxed min and max, which may answer either way on NaN and on signed zeros | Adopted |
| W16 | Order of delivery | Batch first: the default entry routes batch calls, and every stream stays in TypeScript. Streams move to WASM in a later step, with W-O4 settled | Batch needs no change to the stream API | Adopted |
| W17 | Memory | `runtime/wasm.ts` keeps a byte budget: a call whose inputs and outputs exceed it runs in TypeScript. A call that throws inside the module is answered from `./js` and drops the instance, which the next call instantiates again from the compiled module; after a fixed number of such calls the engine is off for the life of the process. An instance whose linear memory passed a high-water mark is dropped once its call has copied its results out | Linear memory never shrinks, wasm32 ends at 4 GB, and an allocation failure in the module is a trap, not a return code. Without the reset one very long call would leave every later call falling through; without the limit a module that traps on every call would cost each call a failed attempt and a new instance | Adopted |

## 3. Open

| # | Question | Settled by |
|---|---|---|
| W-O2 | A second binary with no relaxed SIMD and a software `fma`, for a runtime that fails W4 only on the fused check. Its `fma` must be `runtime/fma.ts`'s algorithm: a libm `fma` compiled to WASM is slower than TypeScript on every multiply-add chain | Its timings against TypeScript on a chain function and on one with no fused site, and the binary's size |
| W-O5 | Auto-vectorisation with only `f64x2.relaxed_madd` relaxed: rewrite each relaxed min and max to `f64x2.pmin` and `f64x2.pmax` after the link | Bits on NaN and signed-zero inputs against the unvectorised module, then timings |
| W-O4 | Releasing a WASM stream. Its state is linear memory, which never shrinks, and [D15](typescript-backend.md) has no `close()`. A `FinalizationRegistry` runs only after a major collection, which small wrapper objects rarely cause, so it bounds nothing by itself. Choices: an explicit `close()` with the registry behind it; streams kept in TypeScript; or the first with a TypeScript stream once WASM memory passes a budget | Owner |
