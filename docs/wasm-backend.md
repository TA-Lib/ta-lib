# WASM engine for the npm package

**Status:** planned, nothing built. The `ta-lib` npm package gains a WebAssembly engine behind the API of [typescript-api-design.md](typescript-api-design.md); the TypeScript library of [typescript-backend.md](typescript-backend.md) stays, as the `ta-lib/js` entry and as the default entry's fallback. Rows marked Ruled are the owner's; Adopted rows stand unless he reopens them; an Open row names the measurement that settles it.

## 1. Scope

- **What ships.** One package, two entries. `ta-lib` runs each call in WASM when the runtime passes the load checks (W4) and in the TypeScript body otherwise. `ta-lib/js` is the TypeScript library alone and never loads WASM.
- **Same values.** The two engines are bit-identical on every call the default entry sends to WASM, so which one answers changes speed only, and the default entry chooses by itself. On a non-finite input the sign and payload of a NaN result may differ between the engines. A call that can reach a transcendental function stays in TypeScript (W10).
- **What does not ship:** a WASM-only entry, an API that must be awaited before its first call, one WASM module per function.

## 2. Decisions

| # | Decision | Choice | Why | Status |
|---|---|---|---|---|
| W1 | Engine | A WASM engine generated beside the TypeScript library, in the same npm package | Software `fma` is TypeScript's dominant cost ([D9](typescript-backend.md)); a hardware fused multiply-add in WASM removes it | Ruled (owner, 2026-11-11) |
| W2 | Entries | `"."`: a generated layer per function that calls WASM when it is loaded and the `./js` function otherwise. `"./js"`: the TypeScript library as it is, with no routing and no WASM glue. Both export the same names and share `Core`, `TALibError`, the enums and the result types | Whoever must not load WASM (a strict Content-Security-Policy, a size budget) imports `ta-lib/js` and gets today's code. Everyone else gets the fast path with no code change | Ruled (owner, 2026-11-11) |
| W3 | FMA | `f64x2.relaxed_madd` (relaxed SIMD), used only where W4 proves it fused | Fused, it gives C's bits. Relaxed SIMD lets an engine compute it unfused, so it is trusted only after the check | Ruled (owner, 2026-11-11): hardware FMA comes first |
| W4 | Load checks | The module compiles, and one multiply-add whose fused and unfused results differ returns the fused one, on operands that reach the module at run time. A failure of either leaves the TypeScript path in place and throws nothing. `ready()` resolves to the engine in use and, for TypeScript, which check failed | Compilation fails where relaxed SIMD is missing and where a Content-Security-Policy forbids WASM; there is no way to ask without trying. Constant operands could be folded at build time, and the probe would then pass on a CPU that does not fuse | Adopted |
| W5 | API | Unchanged and synchronous: no top-level await ([D3](typescript-backend.md)), no call that must be awaited first | The fallback is what makes this possible in a browser, which compiles a module of this size only asynchronously | Adopted |
| W6 | Settings | `Core` stays the JavaScript object of [D12](typescript-backend.md) and the only owner of unstable periods and candle settings. The engine keeps none. Until a `Core` can be passed to the module, a call whose `core` is not `Core.DEFAULT` runs in TypeScript | One source of truth whichever engine answers. A subclassed or non-default `Core` read through the module's own copy would silently answer with other settings | Adopted |
| W7 | Loading | Node, Deno and Bun instantiate synchronously on the first call the routing table sends to WASM, not at import. A browser loads the engine only when the caller awaits `ready()`; before that, and without it, every call runs TypeScript. `ready()` takes engine-loading arguments only; settings stay on `Core` (W6) | A script that never reaches a routed call pays nothing, and importing the package has no side effect. In a browser an explicit call fetches the bytes only for a caller who asked, and a page whose Content-Security-Policy forbids WASM logs no violation unless it called | Ruled (owner, 2026-11-11): explicit `ready()` in browsers. First-call instantiation: Adopted |
| W8 | Source | The module is the generated Rust crate built for `wasm32-unknown-unknown`, behind generated `extern "C"` exports. The crate's fused sites are one macro whose wasm32 arm is `f64x2.relaxed_madd`; the crate stays `#![forbid(unsafe_code)]`. The module is built with relaxed SIMD on and both auto-vectorisers off | The crate builds for that target with its own allocator; a bad index traps where C would corrupt linear memory. The generated C built for wasm32 gives the same bits and, candlesticks apart (#594, #580), the same speed, and would need a C library for the target. With relaxed SIMD on, LLVM turns every vectorised float select into a relaxed min or max, and no spelling of the source avoids it; without the vectorisers the batch tier is 8% slower on average (Xeon, every function, 10,000 bars), the functions that vectorise most by up to 3x | Adopted |
| W9 | Modules | One. It holds the tiers the default entry routes: batch only until streams move to WASM (W16) | A function taking an MA type at run time carries every moving average, so a split by family would repeat that code in each part. The streaming tier is more than half the bytes, and nothing calls it before W16's second step | Adopted |
| W10 | Transcendental calls | A call that can reach a transcendental function ([D11](typescript-backend.md)'s predicate: the function carries `uses_transcendental`, or an MA-type parameter selects MAMA or ALMA) runs in TypeScript. The module imports nothing | A libm inside the module differs from the JS engine's `Math.*` in the last bit, silently, and a recursive filter amplifies it; an import needs `unsafe` in the crate. Either way these calls gain nothing in batch | Adopted |
| W11 | Stream class | One `<N>Stream` per indicator in the default entry, holding a WASM handle or the `./js` stream, each method choosing by that | A call site sees one class whichever engine answers. Timed against a class per engine and a closure, no shape costs more than a few ns per bar | Adopted |
| W12 | Routing | A generated table says, per function and tier, from how many bars the WASM path is taken when the engine is loaded; absent means never. An entry is set only from timings of the public call on intel-1, amd-1 and macos-1, by medians, where WASM is faster on each by a margin | The copy into and out of linear memory outweighs the gain on cheap functions with no fused site and on short series, and the functions that lose differ between x86 and ARM64 | Adopted |
| W13 | Argument contract | `./js` is the authority. The default entry takes the WASM path only when: the routing table names the tier, the caller passes no output buffer, `core` is `Core.DEFAULT`, each integer parameter is an int32 and each real one a number, and the call's bytes fit the memory budget (W17). It converts every input with the `./js` entry conversion before it touches linear memory, sizes each slice in linear memory to the caller's own array length, and derives its views after the last step that can run caller code. The Rust public tier validates the rest and answers an invalid enum with an error. Any other call, any call WASM rejects and any trap is handed to the `./js` function with the caller's original arguments, which answers or throws; an argument whose getter or `valueOf` has a side effect therefore runs twice on a fall-through. A typed array's length is the built-in one, never its `length` property | A rejection always carries the `./js` message and code. Rust sees only the slices the glue builds, never the caller's arrays, so every check on a caller's buffer stays on the `./js` side. A caller's `valueOf` or getter can run during a copy and grow linear memory, which detaches a view taken earlier and drops the rest of the copy silently | Adopted |
| W14 | Packaging | The module ships inside the package as one generated JavaScript file holding its bytes (base64), built by `build-libraries`, never committed. `exports["."]` has a `node`, `bun` and `deno` condition whose entry imports that file statically, and a `default` entry whose `ready()` imports it dynamically; each condition lists `types` first. `"./js"` imports neither. `./metadata` calls the `./js` functions | No `.wasm` asset for a bundler to lose, no `node:` import in the library ([D3](typescript-backend.md)), and a browser bundle that never calls `ready()` does not carry the bytes. A runtime that forbids compiling from bytes (some edge runtimes) stays on TypeScript | Adopted |
| W15 | Gates | The generated server calls through the default entry and takes the engine as a start-up argument, and `ta_regtest --codegen`, `--xlang-hash` and the stream legs run once per engine. A strict mode, used by every gate, throws where the default entry would fall through and ignores the routing table, and a counter of fall-throughs must read zero for every call `./js` accepts. A generated library test calls every function through both engines and compares raw bits, over drawn parameter sets, MA types included. A build check disassembles the module and fails on any relaxed-SIMD instruction other than `f64x2.relaxed_madd`. A bundler build of the `default` entry calls `ready()` | A fall-through answers correctly from TypeScript, so without the strict mode a glue defect makes every engine comparison TypeScript against TypeScript and passes. With relaxed SIMD enabled for a whole crate the compiler also picks relaxed min and max, which may answer either way on NaN and on signed zeros | Adopted |
| W16 | Order of delivery | Batch first: the default entry routes batch calls, and every stream stays in TypeScript. Streams move to WASM in a later step, with W-O4 settled | Batch needs no change to the stream API | Adopted |
| W17 | Memory | The default entry keeps a byte budget: a call whose inputs and outputs exceed it runs in TypeScript. A trap is caught, answered from `./js`, and the module is instantiated again; so is a module whose linear memory passed a high-water mark, while no WASM stream is alive | Linear memory never shrinks, wasm32 ends at 4 GB, and an allocation failure in the module is a trap, not a return code. Without the reset one very long call would leave every later call falling through | Adopted |

## 3. Open

| # | Question | Settled by |
|---|---|---|
| W-O2 | A second binary with no relaxed SIMD and a software `fma`, for a runtime that fails W4 only on the fused check. Its `fma` must be `runtime/fma.ts`'s algorithm: a libm `fma` compiled to WASM is slower than TypeScript on every multiply-add chain | Its timings against TypeScript on a chain function and on one with no fused site, and the binary's size |
| W-O5 | Auto-vectorisation with only `f64x2.relaxed_madd` relaxed: rewrite each relaxed min and max to `f64x2.pmin` and `f64x2.pmax` after the link | Bits on NaN and signed-zero inputs against the unvectorised module, then timings |
| W-O3 | Whether `getRuntimeInfo` reports the engine. The spec has every language answer every key, so the key would be added to C, Rust, Java and C# as well | Owner |
| W-O4 | Releasing a WASM stream. Its state is linear memory, which never shrinks, and [D15](typescript-backend.md) has no `close()`. A `FinalizationRegistry` runs only after a major collection, which small wrapper objects rarely cause, so it bounds nothing by itself. Choices: an explicit `close()` with the registry behind it; streams kept in TypeScript; or the first with a TypeScript stream once WASM memory passes a budget | Owner |
