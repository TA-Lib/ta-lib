# WASM engine for the npm package

**Status:** batch built. The `ta-lib` and `ta-lib/abstract` entries of the `ta-lib` npm package can run the batch tier of every function that cannot reach a transcendental call in a WebAssembly engine, behind the API of [typescript-api-design.md](typescript-api-design.md), for the functions and bar counts the routing table (W12) names; the test modes (W15) send every call W13 admits. Not built: a stream's open in WASM (W16's second step) and the open rows. The TypeScript library of [typescript-backend.md](typescript-backend.md) stays, as the `ta-lib/js` and `ta-lib/js/abstract` entries and as the routed entries' fallback. Rows marked Ruled are the owner's; Adopted rows stand unless he reopens them; an Open row names the measurement that settles it.

## 1. Scope

- **What ships.** One package, four entries. `ta-lib` runs a batch call in WASM when the routing table names it (W12), the call meets W13 and the runtime passed the load checks (W4), and in the `./js` function otherwise; its lookbacks and streams are the `./js` ones. `ta-lib/abstract` is the Abstract API over the same routed calls (W18). `ta-lib/js` and `ta-lib/js/abstract` are the TypeScript library alone and never load WASM.
- **Same values.** The two engines are bit-identical on every call a routed entry sends to WASM, so which one answers changes speed only, and the routed entries choose by themselves. On a non-finite input the sign and payload of a NaN result may differ between the engines, and on an input holding a NaN, whose batch result is unspecified, so may a value, such as the index MAXINDEX returns. A call that can reach a transcendental function stays in TypeScript (W10).
- **What does not ship:** a WASM-only entry, an API that must be awaited before its first call, one WASM module per function.

## 2. Decisions

| # | Decision | Choice | Why | Status |
|---|---|---|---|---|
| W1 | Engine | A WASM engine generated beside the TypeScript library, in the same npm package | Software `fma` is TypeScript's dominant cost ([D9](typescript-backend.md)); a hardware fused multiply-add in WASM removes it | Ruled (owner, 2026-11-11) |
| W2 | Entries | `"."`: a generated layer per function that calls WASM when it is loaded and the `./js` function otherwise. `"./js"`: the TypeScript library as it is, with no routing and no WASM glue. The default entry exports every name `./js` exports, plus `ready` and its status types; the two share `Core`, `TALibError`, the enums and the result types. The Abstract API's two entries: W18 | Whoever must not load WASM (a strict Content-Security-Policy, a size budget) imports `ta-lib/js` and gets the TypeScript library. Everyone else gets the fast path with no code change | Ruled (owner, 2026-11-11) |
| W3 | FMA | `f64x2.relaxed_madd` (relaxed SIMD), used only where W4 proves it fused | Fused, it gives C's bits. Relaxed SIMD lets an engine compute it unfused, so it is trusted only after the check | Ruled (owner, 2026-11-11): hardware FMA comes first |
| W4 | Load checks | The module compiles, and one multiply-add whose fused and unfused results differ returns the fused one, on operands that reach the module at run time. A failure of either leaves the TypeScript path in place and throws nothing. `ready()` resolves to the status at the time of the call, `{ engine, reason }`: `'wasm'` when the engine is loaded, else `'js'` and the step that failed (bytes not importable, compile, instantiate, the fused check), that the engine is not loaded yet, that traps turned it off (W17), or that the entry has no engine (W19). Concurrent calls share one load. After `'unavailable'` on an entry that has an engine, a later `ready()` imports the bytes again; no other failure is retried. `getRuntimeInfo` reports per entry as the keys `wasm.engine` and `wasm.reason`, which only TypeScript answers: `ta-lib/abstract` the state of the engine its calls route to, `ta-lib/js/abstract` and the engine-less abstract entry 0 and the `'unavailable'` code. Asking loads nothing | Compilation fails where relaxed SIMD is missing and where a Content-Security-Policy forbids WASM; there is no way to ask without trying. Constant operands could be folded at build time, and the probe would then pass on a CPU that does not fuse. A fetch of the bytes chunk can fail transiently; a compile, instantiate or fused-check failure gives the same answer on a retry | Adopted; reported by `getRuntimeInfo`: Ruled (owner, 2026-11-12), every backend answers the common keys and only the backend that has a thing answers a key describing it |
| W5 | API | Unchanged and synchronous: no top-level await ([D3](typescript-backend.md)), no call that must be awaited first | The fallback is what makes this possible in a browser, which compiles a module of this size only asynchronously | Adopted |
| W6 | Settings | `Core` stays the JavaScript object of [D12](typescript-backend.md) and the only owner of unstable periods and candle settings. The module holds only the default settings, and until a `Core` can be passed to it, a call whose `core` is not `Core.DEFAULT` runs in TypeScript | One source of truth whichever engine answers. A subclassed or non-default `Core` read through the module's own copy would silently answer with other settings | Adopted |
| W7 | Loading | Under the `node`, `bun` and `deno` export conditions the engine instantiates synchronously on the first call the routing table sends to WASM, not at import; awaiting `ready()` first moves the compile out of that call. Under `default` (browsers, and any bundle built without the `node` condition) the engine loads only when the caller awaits `ready()`, per realm, so each Worker calls it itself; before that, and without it, every call runs TypeScript. Under `workerd`, `edge-light` and `react-native` there is no engine (W19). `ready()` takes no argument; settings stay on `Core` (W6) | A script that never reaches a routed call pays nothing, and importing the package compiles nothing. In a browser an explicit call fetches the bytes only for a caller who asked, and a page whose Content-Security-Policy forbids WASM logs no violation unless it called | Ruled (owner, 2026-11-11): explicit `ready()` in browsers. First-call instantiation: Adopted |
| W8 | Source | The module is the generated Rust crate built for `wasm32-unknown-unknown`, behind the generated export crate `ta_codegen/output/wasm`, one `extern "C"` batch export per function. The `ta-lib` crate's fused sites are the `fmadd!` macro, whose wasm32 arm is `f64x2.relaxed_madd`, and that crate stays `#![forbid(unsafe_code)]`; the slices over linear memory are formed in the export crate, which declines a misaligned slice and an output overlapping any other slice, and refuses a slice outside the scratch the last `scratch` call handed out with a code of its own, reason `'frame'`, which every gate counts as a defect. `scripts/build.py wasm` builds it with relaxed SIMD on, both auto-vectorisers off, the source paths remapped and the linker writing each index in its shortest encoding, and the crate's release profile strips the name, producers and target-features sections; `bin/ta_lib.wasm` is the linker's output, with no optimisation pass after the compiler's | The crate builds for that target with its own allocator; a bad index traps where C would corrupt linear memory. The generated C built for wasm32 gives the same bits and, candlesticks apart (#594, #580), the same speed, and would need a C library for the target. With relaxed SIMD on, LLVM turns every vectorised float select into a relaxed min or max, and no spelling of the source avoids it; W-O5 is the way back to vectorised loops. The compressed size is what a caller downloads; the strip removes only custom sections, which no runtime reads, and leaves the code section byte for byte as the linker wrote it | Ruled (owner, 2026-11-12): stripped, with no optimisation pass. The rest: Adopted |
| W9 | Modules | One, exporting the batch tier of every function W10 admits, whatever the routing table holds; a stream's open joins it at W16's second step | A function taking an MA type at run time carries every moving average, so a split by family would repeat that code in each part. A routing-table edit changes no binary, and the test modes reach every export | Adopted |
| W10 | Transcendental calls | A call that can reach a transcendental function ([D11](typescript-backend.md)'s predicate: the function carries `uses_transcendental`, or an MA-type parameter selects MAMA or ALMA) runs in TypeScript: such a function has no export, and an export declines an MA type that selects one. The module imports nothing | A libm inside the module differs from the JS engine's `Math.*` in the last bit, silently, and a recursive filter amplifies it; an import needs `unsafe` in the `ta-lib` crate. Either way these calls gain nothing in batch | Adopted |
| W11 | Stream class | A stream is a TypeScript object in both entries: the default entry re-exports the `./js` stream class and openers, and no stream state stays in linear memory. `update` and `peek` never call the module | One bar is too little work to repay a call into the module. State in linear memory would need a release, and [D15](typescript-backend.md) has no `close()`. With one class, a stream passes between code importing either entry | Ruled (owner, 2026-11-17) |
| W12 | Routing | A table, `ta_codegen/input/wasm_routing.yaml`, says, per function and tier, at which bar counts the WASM path is taken when the engine is loaded: from a count on, or within an inclusive range; absent means never. An entry is set only from timings of the public call on intel-1, amd-1 and macos-1, taken under V8's `--single-threaded-gc`, by `scripts/wasm_routing_table.py`, which drops a timing that spans more than two major GCs: a measured bar count wins when, on each host, WASM's upper quartile is below TypeScript's lower quartile by a margin, and is a loss when, on some host, WASM's median is slower than TypeScript's by more than a small tolerance. The entry is the run of consecutive counts without a loss, from a win, ending at a win or at the largest measured count, that holds the most wins (at least two unless it reaches the largest count) and more wins than counts no host routes, at larger counts on a tie: open when it reaches the largest measured count, else a range; a previous entry stays while its ends are measured counts, it has no loss and more wins than counts no host routes, and the rule's own entry has its form with at most one more winning count and at most one fewer count no host routes | The copy into and out of linear memory outweighs the gain on cheap functions with no fused site and on short series, and the functions that lose differ between x86 and ARM64 | Adopted |
| W13 | Argument contract | `./js` is the authority. A routed entry takes the WASM path, in the options form and in the `<n>Positional` form the Abstract API calls, with or without caller output buffers, only when the routing table names the tier at the input's length, or a test mode forces it (W15), and: the options are omitted or an object `./js` accepts as one; `core` is omitted or the `Core.DEFAULT` object itself, so a `new Core()` with default settings does not qualify; each range bound and integer parameter is an int32 and each real one a number; every input has the same `length`; the range lies inside the input; each output buffer is an instance of its class, holds at least the count `./js` requires, and shares no byte with another buffer or a typed-array input, an in-place call included, while buffers apart in one `ArrayBuffer` qualify; each input, converted as `./js` converts it (a `Float64Array` as it is, anything else through `Float64Array.from`), holds that length, tested after the last conversion; and the call's bytes fit the memory budget (W17). Every check but the converted length precedes the first conversion, except that without output buffers it is the module that rejects an out-of-range parameter, after the conversion; no caller code runs between the last check and the copy out, and every output is copied out before a result view is built. Views over linear memory are derived after the last step that can run caller code. Arguments are trusted to be ordinary arrays: an own property shadowing a built-in one, a Proxy, argument conversion code that changes another argument, or another thread resizing a buffer during the call gives an unspecified result, which still writes nothing outside the caller's arrays and the engine's memory. The export declines an enum value it does not know or that W10 keeps in TypeScript; the Rust public tier validates the rest. Any other call, any call WASM declines or rejects and any trap is handed to the `./js` function with the caller's original arguments, which answers or throws; an argument whose getter or `valueOf` has a side effect therefore runs twice on a fall-through | A rejection always carries the `./js` message and code, so a buffer `./js` would reject, or would compute in place with bodies that may use it as scratch, falls through. Rust sees only the slices the glue builds, never the caller's arrays, and the JS engine bounds-checks every copy into linear memory and into a caller's array. Checking before converting means a call `./js` rejects for its range or its buffers runs no `valueOf` in the glue either. A caller's `valueOf` can call a routed function back and grow linear memory, which detaches a view taken earlier and drops the rest of a copy through it silently | Adopted |
| W14 | Packaging | The module ships inside the package as one JavaScript file holding its bytes (base64), `runtime/wasmBytes.js`, never committed: `scripts/ts_wasm_bytes.mjs` writes it from `bin/ta_lib.wasm` after `tsc`, into `dist/` for `build-libraries` and beside the server's compiled library for the server build, and refuses a `bin/ta_lib.wasm` older than the crates' sources. `exports["."]` and `exports["./abstract"]` each have, in this order, `workerd`, `edge-light` and `react-native` conditions naming the engine-less entry (W19), `node`, `bun` and `deno` conditions whose entry imports that file statically, and a `default` entry whose `ready()` imports it dynamically; each subpath and each condition list `types` first, and `sideEffects` names the two static entries. `main` names the default entry and a top-level `react-native` field the engine-less one, for resolvers that ignore `exports`. `"./js"` and `"./js/abstract"` import neither. `./abstract` calls the routed `<n>Positional` of each function with a WASM export and the `./js` one of every other; `./js/abstract` calls only the `./js` ones | No `.wasm` asset for a bundler to lose, no `node:` import in the library ([D3](typescript-backend.md)), and a browser bundle that never calls `ready()` does not carry the bytes. Without the `sideEffects` entries a bundler may drop a static entry's hand-over of the bytes | Adopted |
| W15 | Gates | Two test modes ignore the routing table and route every call W13 admits: `force` falls through as the table does, `strict` throws where a call `./js` accepts would fall through. The generated server started with `--engine=wasm` runs its batch correctness calls through the default entry and its abstract calls through `ta-lib/abstract`, in `force` mode, and adds per-call engine evidence to each reply; ta_regtest runs it as `tswasm`, its abstract block and buffered share included, and what fails the run is the [section on `tswasm`](../src/tools/ta_regtest/CLAUDE.md). The generated `test/engineParity.test.ts` runs in `strict` mode and compares raw bits with `./js` for every exported function, in the options form with and without buffers and in the positional form, over default, minimum and drawn parameter sets, every MA type W10 admits included, and compares `ta-lib/abstract` with `ta-lib/js/abstract`, which must never enter the module. The generated `test/engineRouting.test.ts` runs the table mode against the routing table, read by the generator apart from the routed modules, in the options form with and without buffers and in the positional form: under each entry's first bar count the call stays in TypeScript, at it the call runs in WASM, a range's last bar count runs in WASM and one bar over stays in TypeScript, and an untabled function never does. `test/abstractEngine.test.ts` runs every function through `ta-lib/abstract`, installed from the tarball, against `ta-lib/js/abstract` in `force` mode: each call runs in WASM exactly where the function has an export. `scripts/check_wasm_module.py` decodes the module and fails on an import, on any relaxed-SIMD instruction other than `f64x2.relaxed_madd`, on too few function bodies besides `fma_probe` using that one, on a custom section and on the build machine's repository or home path. `scripts/ts_package_check.py` bundles the installed tarball with esbuild for Node: through the default entry and through `ta-lib/abstract` alone, a routed call with no `ready()` must run in WASM with no fall-through; `ta-lib/js` and `ta-lib/js/abstract` bundles must load no engine module; and under each engine-less condition, bundles of `ta-lib` and of `ta-lib/abstract` must load the engine-less entry, give the `./js` bits and have `ready()` resolve to `'unavailable'`. In the nightly, `scripts/ts_browser_check.py` bundles the packed package with esbuild for the browser platform and runs it in headless Chrome: `ready()` resolves to `'wasm'` with no synchronous compile, strict-mode calls with and without fused sites give the `./js` bits and each moves the module's call counter, a call before `ready()` stays in TypeScript, the bytes chunk is fetched only once `ready()` is called and the `ta-lib/js` and `ta-lib/js/abstract` bundles hold none of the bytes; under a Content-Security-Policy that forbids WASM, `ready()` resolves to `'js'` with reason `'compile'`, every call answers with the `./js` bits and nothing throws; on the `ta-lib/abstract` page, a call before `ready()` stays in TypeScript and fetches no bytes, and after it the same call enters the module with the `./js` bits | A fall-through answers correctly from TypeScript, so a gate that neither throws on one nor counts them makes every engine comparison TypeScript against TypeScript and passes. The server uses `force` because the harness also sends calls `./js` accepts that fall through by design (a non-default `core`, inputs of unequal length, an aliased buffer, an MA type W10 keeps in TypeScript), which `strict` would turn into errors; the evidence tells those from a defect. With relaxed SIMD enabled for a whole crate the compiler also picks relaxed min and max, which may answer either way on NaN and on signed zeros | Adopted |
| W16 | Order of delivery | Batch first: the default entry routes batch calls. In a second step a stream's open over its history may run in WASM, the state copied out into the TypeScript stream (W11), routed per function and bar count as W12 routes batch | The open is batch-shaped work, and neither step changes the stream API | Ruled (owner, 2026-11-17) |
| W17 | Memory | `runtime/wasm.ts` keeps a byte budget: a call whose inputs and outputs exceed it runs in TypeScript. A call that throws inside the module is answered from `./js` and drops the instance, which the next call instantiates again from the compiled module; after a fixed number of such calls the engine is off for the life of the process. An instance whose linear memory passed a high-water mark is dropped once its call has copied its results out | Linear memory never shrinks, wasm32 ends at 4 GB, and an allocation failure in the module is a trap, not a return code. Without the reset one very long call would leave every later call falling through; without the limit a module that traps on every call would cost each call a failed attempt and a new instance | Adopted |
| W18 | Abstract API | `ta-lib/abstract` routes each call exactly as the default entry does, and exports `ready` and its status types. `ta-lib/js/abstract` is its twin over `./js` alone and never loads WASM. The two share every class (`FuncInfo`, `ParamHolder`, the flags); each has its own `Functions` catalog, of type `FunctionCatalog`. Either references every function | A program that picks functions at run time gets the engine with no code change, and one that must not load WASM has an entry for it. With one set of classes a holder's types do not depend on the entry. Since either catalog reaches every function, `ta-lib/js/abstract` saves the engine and its bytes, not unused functions | Ruled (owner, 2026-11-17) |
| W19 | Engine-less entries | Under `workerd`, `edge-light` and `react-native`, `"."` and `"./abstract"` resolve to entries with the same names and no engine module: every call runs in TypeScript, `ready()` resolves to `{ engine: 'js', reason: 'unavailable' }`, and that answer is permanent | Those runtimes cannot compile WebAssembly from bytes, and their bundlers inline the bytes chunk, so the routed entries would only add the bytes to the bundle | Ruled (owner, 2026-11-17) |
